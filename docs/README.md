## 1. 定位

**Excalibur = 参数选择器。**

凡是「命令我会写,但那个**参数**我记不住 / shell 补全不了」的场合,给一个键盘驱动的
选择器,选完把**完整命令吐回 shell**(`ModuleAction::Output` / `OutputAndExecute`
+ fish 的 `ex`)。

这个定位取代了旧表述「把命令吐回 shell 的 shell 集成」。区别很重要:

- **吐命令回 shell 是机制,不是价值。** navi 也吐命令、fish abbrev 也吐命令。
- **价值在「补上 shell 补不了的那段参数」。** 这才是没人做的部分。

现有模块在这个视角下是同一件事,只是选的参数不同:

| 模块 | 选的参数 | 吐命令? | 设计文档 |
|---|---|---|---|
| history | 一整条命令(**最弱的一种**,见 §2.4) | ✅ Enter / Ctrl+O | — |
| proctrace | 一个 pid / systemd unit / cwd | ✅ `l`/`r`/`x`/`c` | — |
| settings | 一个 profile | ❌ 自己落地 | — |
| ssh | 一台主机 + 一条转发规则 | ❌ 自己落地 | `docs/ssh.md` |

「自己落地」不算偏离定位 —— 吐命令始终只是机制,选参数才是价值。

**这个定位验证过一次(2026-08-23)**:proctrace 从只读 dashboard 变成参数选择器
只花了 ~40 行(`emit_from_selection()` 纯格式化,因为 pid / unit / cwd 查询时
早就解析出来了)。说明这个抽象是贴着现有架构长的,不是硬套。详见 commit `75788d5`。

### 吸收标准

**摩擦 × 有没有现成好工具,而不是频率。** 高频但低摩擦、且已有好工具的 → 不吸收。

已判定出局:

- ❌ **git**:频率之王,但有 abbrev + 补全,每次几乎零摩擦,picker 赢不了肌肉记忆。
- ❌ **dev-utils(hash/base64/uuid/jwt…)**:两台机器 history 里零出现,且是
  copy-to-clipboard,用不上差异化。
- ❌ **单纯的「挑主机 + ssh 连接」**:fish 自带 ssh 补全已零摩擦,且 sshm / hop /
  fast-ssh / sshs 这个 niche 已很拥挤。

对已被成熟工具统治的领域(git 全功能客户端、文件管理、系统监控、docker/k8s),
策略是**整合 / 启动外部工具**,不自研。

## 2. 定量依据(2026-08-23,本地 fish history 2344 条)

原结论建立在「频率」上。复核发现三件事,直接推翻了它。
**这一节是整份文档里最贵的部分** —— 它是在特定机器、特定日期量出来的,丢了就得重量。

### 2.1 fish history 是去重的 —— 所有「频率」其实是「参数变体数」

2344 条里只有 20 条重复,基本是并发 session 合并的残留。所以
`kami 上 rsync 740` 不是「跑了 740 次 rsync」,而是「写过 740 条**互不相同**的 rsync」。

本地实测,逐字重复率基本为零:

| 命令 | total | distinct |
|---|---|---|
| `cd` | 631 | 625 |
| `rsync` | 104 | **104** |
| `systemctl` | 43 | 43 |
| `rm` | 49 | 49 |

### 2.2 但抽掉参数后立刻塌缩成少数模板

104 条互不相同的 rsync,84 条落进 4 个模板:

```
rsync -av <HOST:PATH> .                          27
rsync -av lxb@<HOST:PATH> .                      21
rsync -av --checksum --progress <HOST:PATH> .    20
rsync -av .<PATH> <HOST:PATH>                    16
```

全局:2288 条 distinct 命令 → 1444 个形状(粗糙正则抽象,长命令压缩率远高于此)。

### 2.3 fish 对远端路径零补全

`__rsync_remote_target`(fish 自带 completions/rsync.fish)的实现是把你**已经敲的字
原样回显**,只为防止补全回退到本地文件 —— 它根本不 ssh 出去列目录。
而本地 `cd` 的 625 条路径互不相同、深达 80+ 字符
(`/var/lib/wonder/warehouseBishopNFS/warehousePool/parquet/…`)。

### 2.4 结论

**摩擦不在「哪条命令」,在「哪个参数」;而参数几乎全是「路径」和「主机」。**

推论:一个「回忆整条历史命令」的浏览器(= 现在的 history 模块)在优化一个
**很少发生**的场景 —— 长命令几乎从不逐字复用。history 模块的未来应是
**从历史里提取模板 + 参数槽**,而不是继续优化整条命令的搜索排序。

## 3. 路线图与待落地

### 3.1 SSH 模块(进行中)

第一版已合并(PR #3):三层连通性仪表盘、六字段 config 表单、遮蔽检测、
按 argv 认领 / 按 pid 停。110 个测试。

**待落地共 11 项,分四组,细节全在 `docs/ssh.md` §9:**

| 组 | 内容 | 来源 |
|---|---|---|
| A | 转发组要看得见 / 要能建 / 多选启动 | 2026-08-29 使用反馈 |
| B | 流向图形化、仪表盘统计(运行时长 + 吞吐 + sparkline) | 2026-08-29 使用反馈 |
| C | 存盘前语法校验、撤销与备份语义、无主隧道 | 设计里承诺过但没落地 |
| D | 远端端口发现、host 新建/克隆、块内多行编辑 | 原计划剩余 |

C 组是**已经写进设计、但第一版没做**的三条,其中「无主隧道」是一个当前活着的
静默失败(改了正在跑的规则,旧进程还占着端口却从面板上消失),便宜,可以插队。

### 3.2 history → 模板化(下一个模块级改造)

§2.4 的直接推论,也是整份定量复核里唯一还没兑现的结论。把 §2.2 的形状聚类做进
history 模块:同一模板下的历史命令折叠成一条,参数变成可填的槽。

现状是「按整条命令搜索排序」,而数据说整条命令几乎从不逐字复用 —— 这个模块正在
优化一个很少发生的场景。**优先级仅次于 SSH 收尾。**

### 3.3 settings 模块:准备砍掉

2026-08-29 决定。它是这批模块里唯一**不选参数**的 —— 每个动作都是自己落地的
文件操作,跟 §1 的定位关系最远,而 Claude Code 自己的配置管理也在演进。

未定:是直接删,还是留着不再投入。**删之前需要确认没有在用**,别顺手删掉。

### 3.4 远端路径浏览器(降级保留)

§2.3 的定量依据仍然成立(fish 对远端路径零补全,`__rsync_remote_target` 只回显;
104 条 rsync 全不重复)。选主机 → `ssh ls` 走目录树 → `t` 吐 rsync 拉取行。
与 SSH 模块共用 `sshconfig.rs` 的主机发现,等 SSH 收尾再排期。

待定:远端 `ls` 的延迟(每层一次 ssh 往返)。备选复用 ControlMaster 或一次性
`find -maxdepth N`。**实测再决定,不预先优化。**

### 3.5 更远

- **nix 工作流助手** —— kami 上 ~900 条又长又难记的 nix 咒语,几乎没有好 TUI。
- (按需)**外部工具启动器** —— 为 git / 文件 / 监控等成熟领域提供一键跳入,不自研。

### 3.6 一件一直没人工确认的事

**proctrace 的 emit 端到端效果从未被人按过。** 需要交互式终端,自动化环境里跑不了。
已验证的只到:`cargo build` 通过、三个 fish 文件 `fish --no-execute` 语法通过、
`set -l out (cmd); set -l code $status` 的状态传递单独实测过(0 和 10 都正确)。

`ex t` 的日常使用只证明了 wrapper 能进 TUI —— ssh 模块**不吐命令**,走不到
exit 0/10 那条路径。真正要确认的是:`ex pt` 里按 `x`,`kill <pid>` 有没有落到
命令行上。**一次人工确认即可关掉这条。**
